## MUST

1. **The negative-base-beta exclusion makes the run-2 gate a coin flip for a clean plant latent.**
   `crosscoder.py:256` keeps a latent only if `eps_base >= 0` and `r_base >= 0`. A latent that carries a fine-tune-only
   direction has a base decoder near zero. Its two base betas are then near zero too, and their signs are noise. The
   evidence is the one this plan cites for its "PASS, lean 0.8". E212's planted lead (`run3_planted.json`) had
   ν_r = −0.0035 and ν_ε 0.021, scored 2026-11-18, before the exclusion was added (1a36e7d6, 2026-11-23).
   `negbeta_rescore.json` `.runs["E212"]["planted.L1"]` rescored it: `new.parts.ft_specific` 0 (was 0.766) and
   `counts.ft_specific` 0, so under the rule E311 runs, **E212's plant misses**. The plan's line "E212's spread plant
   already passed under the same recipe" (plan:14, :39) and the b/c prediction (`predictions.json` "0b random") rest
   on the old scoring.
   - The scenario: pods b and c each isolate the plant cleanly (rn ~0.93, ν_ε ~0.02). Each has a sign coin flip on
     β^r_base, and maybe another on β^ε_base. With one flip, both miss with probability ~0.25. With two independent
     flips, both miss with probability ~0.56. That fires the ruled "b and c both miss → run-2 pods terminated" for a
     reason that says nothing about whether the crosscoder isolates a fine-tune-only direction. A b/c split, which
     counts as a miss, is likelier still. Minder et al. p. 26 report "None in BatchTopK" negative-β latents. In their
     setting the filter is a no-op. Here it decides the gate.
   - Where it is read: `run.py:200` (`lead.specific`) and `crosscoder.py:417` (`specific` = `g[""]["ft_specific"]`,
     which goes through `specific()`). The same sign noise touches any truly fine-tune-only latent on the 48 states.
     There it moves change from "specific" to "artefact", which lowers `d_authors`' specific part and leaves `d_alt`
     alone.
   - Fix (a rule change, so it goes to whip-lead/user before any pod starts; $0): decide and file in
     `predictions.json` (it is not yet run, so the edit is a pre-run filing, not a refile) one of the following.
     (a) The gate reads the authors' ν test without the exclusion for the plant, or with the exclusion applied only
     when a base β is below minus a noise floor measured in the same job (e.g. the spread of base β over the self
     control's latents in pod a). (b) Keep the rule, but make the kill rule read `lead.nu_r`, `lead.nu_eps` and the
     raw base betas, not `specific`. Whatever is chosen, log the lead's four betas: today `rec["lead"]` (`crosscoder.py:416-417`)
     holds ν_r and ν_ε only, so a miss from the exclusion can be told apart only by a negative ν. Also restate b/c's
     expected value against E212's rescored miss.

## Checked, no issue

- **The stream and E203.** Key-value sides: `pile_rows`, `per_chunk` (13,082), the chunk permutation (seed + e), the
  window seeds (`seed*7919 + c`), the shuffle generator and the chunk-skip resume are identical to `Job.text`, `plan`,
  `chunk` and `stream`. `n_pile` is a multiple of `chunk_rows`, so E203's partial last chunk never arises.
  `CC.batches` is E203's skip loop.
- **The plant and E203.** The answer placement adds `vec` at column `half` of task windows only, as E203's
  `acts(pos=half)` did. Its read is at column `half` of every score window; validation rows are unplanted; the base
  side is never planted. `planted()` is E203's (same seed, median norm at the answer position). Masks are generated
  per (epoch, chunk), so a resume gets the same masks.
- **Scoring.** `Sides.score` is `CC.score` plus step, tokens and `max_rn_dev_alive`, which is E203's `Job.score`
  minus `jaccard_prev`. The latent-scaling targets (error plus the latent's own base or fine-tune contribution,
  reconstruction, probed with d_ft, normalised space) match the module docstring and the toolkit reference.
- **The long arm.** The trainer has no LR decay (`decay_start=None`) and the same warm-up and k anneal. Epochs 0-1
  use E203's permutations, so the 0.25 snapshot (200M tokens, step 97,656) is E203's end state up to GPU
  nondeterminism. The prediction "reproduces E203" is well posed.
- **Early checks.** They fire on the first curve record at step ≥ 1,000 (batch FVE, then ms per step × total steps,
  which has one or two chunk builds in its 500-step window) and on the first snapshot (FVE, dead). Stage 2 makes a
  new check closure per side. Snapshots are off there, so only the curve checks fire before the end-of-side FVE and
  dead bars.
- **Edge cases.** The self side has zero change: `energy` 0, `lead` −1 and no `lead` key, `specific` 0.0 from empty
  masks, `shared_frac` nan. Its checks read `max_rn_dev_alive` (nan → fail-safe), `counts` and FVE only. A nan part
  or ratio fails every comparison, which is a miss, never a pass. `top()` breaks ties stably.
- **Precision and memory.** `allow_tf32 = False`, the trainer runs in fp32, and the key-value chunk pairs are
  ~6.4 GB with a peak of about 2-3× that, against E203's measured 14.9 GB. Host memory holds the 801 MB Pile file,
  268 MB of pool and 34 MB of val.
- **JSON keys `plot.py` reads.** sides: `kind`, `state`, `key`, `d_authors`, `d_alt`, `specific`, `shared_frac`;
  stage0b: `where`, `seed`, `planted.{key,specific,lead}`, `planted_pass`; E203's `checks["b planted: found,
  specific and carried"].{part,lead}`. All are present.
