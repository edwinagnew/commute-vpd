# Review: E69, the GRPO loop on Qwen3-1.7B, plan and code before the paid run

*2026-11-03. The one review of a gated run (`.claude/CLAUDE.md`, gate 5), by an agent that wrote neither. Read: `reports/plans/2026-11-03_plan_e69-grpo-loop.md`, `src/commute/qwen_rl.py`, `experiments/qwen_rl/{run,job,fetch}.py`, `RUN_BRIEF.md`, `predictions.json`, both sbatch files, the tests, and the helpers they call (`qwen_sft`, `qwen_train`, `qwen_updates`, `qwen_eval`, `qwen_files`). No model loaded, no GPU job.*

The measurement code is sound: I found no bug in the policy gradient, the sampler, the arms' data, the resume or the scoring rules. What can still waste the money is around it: the δW are declared safe on evidence that does not cover them, the plan's most likely bad branch has no code, and two recovery paths are missing. Fix 1 and 2 before the go-ahead; 3 to 5 are cheap and worth doing in the same edit.

## Findings, by consequence

**1. The pod can be terminated with δW missing from W&B, and nobody would know until the fetch.** `Uploader.add` queues with `log_artifact` and does not wait (`qwen_sft.py:339`); `finish` calls `run.finish()` and logs how many were *queued* (`:345-347`). Nothing reads whether an upload succeeded. `SHA256SUMS` is written before the upload (`job.py:165-171`), so it lists what was saved, not what arrived. The terminate rule checks only that `score.json` and `SHA256SUMS` match on both sides (`RUN_BRIEF.md:52`); the first comparison with W&B is the fetch, which runs after termination (`RUN_BRIEF.md:58-62`). The rehearsal does not cover this size: the tiny run's cap skipped every δW (`RUN_BRIEF.md:24`), so only small files went up. Pod disk dies with the pod, so a failed upload loses that δW with no way back short of rerunning the arm, and the δW are the run's only purpose. **Fix:** a pod-side check before `terminate()`: for each `SHA256SUMS` row, `wandb.Api().artifact(<name>:latest)` is committed and its entry's size and md5 match the local file. Make it a stage (`--stage verify`), exit non-zero on a miss, and add it to the terminate rule. Also run it once after R, so an upload problem shows before N and F are paid for.

**2. Branches R2 and R3 cannot run, and R2 is a live possibility.** `lr` is a field of the frozen `Config`, with only `full` and `tiny` sizes and no flag (`job.py:51`, `:86-89`; `run.py:323-326`). A rerun at 3e-6 or 3e-7 therefore needs code written while the pod bills. Done naively, it shares `R.json`, the rollout folders and the artifact names, so `:latest` and `SHA256SUMS` would then point to the rerun, not the 1e-6 δW. The tree also does not say what N and F do after it (plan:131-132): P3 and P4 read N against R at one rate, so N at 1e-6 beside R at 3e-6 is not a null for it. R2 is not remote. Filed expectation: +0.03 to +0.08. Nearest reference: E45's own-samples SFT at peak 1e-5 reached |δW| 1.87 at step 100 and +0.037 (trained under rounding, read at full precision). R's |δW| reads 0.035 and 0.055 at steps 1 and 2, which looks like a random walk, so about 0.4 to 0.6 at step 100 is my rough extrapolation, not a measurement. The scoping report found no published run of this setting (`2026-10-27_analysis_qwen-rl-gsm8k.md:255`). With SE about 0.011, "learns" needs about +0.021. **Fix:** add `SIZES` entries now (for example `lr3e-6`, with its own `out` and `prefix`), and state in the tree whether N and F wait for the R rerun and at which rate they run. Decide before the go-ahead whether the pod waits or terminates on R2.

**3. A crash in `finish_arm` throws away up to 50 steps.** The last checkpoint is at step 50 (`job.py:57`), and `__post_init__` forbids one at the last step (`:76`). The accuracy pass, the tar and the uploads come after step 100 (`run.py:270-282`), so any crash there (process, kernel, W&B) resumes from 50 (`run.py:180-191`): about 1.2 h, about $5 per arm, and `resume` needs nothing else. Memory is not the likely cause: 128 rows × ~700 tokens × 228 kB is about 20 GB beside about 24 GB, under 80. But this path beside Adam has run only at 8 problems. **Fix:** allow the last step in `ckpt_steps` and write it. `range(start + 1, steps + 1)` is then empty, and `finish_arm` runs directly. Cost: one 17 GB write per arm, deleted at the end.

**4. Pod loss has no recovery recipe, and one miss surfaces hours late.** The plan accepts losing the arm in flight (plan:152), but a new pod lacks `rollouts/H.jsonl` and `acc/W0_*.jsonl`, while `A0.json` and `S.json` still say done, so `begin` passes. Missing H crashes at the first read (`job.py:223`), which is cheap. Missing `acc/W0_*` crashes only in `finish_arm` (`run.py:272`), after the whole arm, then resumes from 50. `fetch.py:33` writes only to the cluster's path, so it cannot restore them on a pod, and the brief's crash line covers only a live pod (`RUN_BRIEF.md:34`, `:54`). The new pod also needs the current `SHA256SUMS` synced, or `publish` starts a new file without the earlier arms' rows. CLAUDE.md records a pod that died 75 min into a run with no config change, so over 9 h this is not remote. **Fix:** a `--root` argument on `fetch.py`, a three-line recipe in the brief, and a check at the top of `stage_arm` that both files exist.

**5. The pod's sampler check will stop a healthy run about one time in ten.** Two independent-ish 2 SE tests (`run.py:132-133`, `sampler_se_mult`) give up to about 9% false misses with the sampler correct, and a miss exits 2 and parks a billing pod until someone decides. The sampler has already passed twice on the L40 (jobs 50077, 50208). **Fix:** on the pod, log it and do not stop, or stop only past 3 SE. Change the filed value before the run, with a dated note.

**6. `tee` hides the exit codes the brief relies on.** The commands are `python ... | tee ...` with no `pipefail` (`RUN_BRIEF.md:36-41`), so a stop (exit 2) reads as 0. The `done` flags keep the next stage from running (`job.py:157-162`), so no wrong result follows, but a runner watching exit status sees success and then a refusal that also reads 0. **Fix:** `set -o pipefail` in the brief, or tell the runner to read `"stopped"` and `"done"` in the stage's JSON.

**7. The plan's record does not match the code or the logs (text only; no effect on the run).**
- Plan:188, "Peak 39.8 GB while sampling": that peak is taken after `generate` (`run.py:130`), so it is `generate`'s at 226 rows, not the sampler's. The sampler beside Adam first gets its own peak in S's final `peaks`.
- Plan:146 says rows come from the card's *free* memory; the code uses *total*, deliberately (`qwen_rl.py:187-190`).
- Plan:183 says no live step followed the resume. True of R and N, not of F: job 50074's step 3 was live, |δW| 0.0569 to 0.0681.

**8. Gate 3 was still open at this review.** Job 50077 ran out of memory in the readout, so `seconds.read`, `seconds.f_train` and the sampler's own peak were never recorded. Job 50208, at 2048 tokens, had passed the sampler check and step 1 and was still running when I finished. Its `S.json` numbers belong in the plan before the go-ahead. On the H100 `rows_for` gives 512 rows against this job's 356 (card total about 85 GB), so scale its sampler peak by about 1.44 and compare with 80 GB.

## Looked at and found nothing

- **Policy gradient sign and weights:** none. `weighted_step` minimises w·NLL, so a positive weight raises log-prob. Masks cover response tokens including the end token. Group means are right, a skipped weight of 0 gives the same gradient, and the divisor is the same in all arms. Tests compare with a hand-written loss.
- **On-policy:** none. R and N sample from the live weights in fp32 with no autocast anywhere in the arm path; F is off-policy as planned, from W0.
- **Step numbering and saves:** none. Step t's rollouts come from W_{t-1}; δW and reads are W_t. The P6 and reward-change windows index correctly, including after a resume.
- **Sampler:** none. Left padding, position ids (`next_pos + n_new - 1`), per-row window, an end token exactly at the cap, and cache selection all check out by reading and by test. Generation-config filters are off.
- **Truncation and reward:** none.
- **RNG and identity:** none, with one limit. The seed is set per step, so a resume needs no RNG state. Identity across processes has been seen only at tiny size; S's step 1 matched its own sampler within one process at full size.
- **F's data:** none. **Null shuffle:** none, zero-mean by construction, seeded per problem.
- **Adam, skipped steps, resume:** none. I ran `checkpoint` then `resume` with fused AdamW on CPU, and four steps through a resume at 2 equal four straight steps bit for bit (`~/commute-data/scratch/qwen-rl-lead/e69-review/resume_parity.py`). `load_state_dict` keeps `step` as fused needs.
- **Readouts:** none. KL direction is π₀ ‖ π_t, ΔR is W_t minus W0, and the zero at W0 is exact.
- **Early-check bands:** none. The KL band fits E45's first 1e-6 steps, own 0.0057 and null 0.0067 on maths rows, so R is unlikely to be stopped by it.
- **P0 reference:** none. E61 reads W0 at full precision against bf16 with paired difference 0, se 0.0061.
- **Scoring rules P0-P7:** none, including empty pool, zero SE, ties, N cut and missing stages. 46 tests pass.
- **Fetch and artifact names:** none besides finding 1. Names do not collide, and rehearsal job 50076 worked for small files. Cluster disk has 5.1 TB free.
- **Memory on 80 GB:** none expected, subject to finding 8. **Disk at 250 GB:** none, about 140 GB used at peak.
- **Plan against code, recipe:** none besides finding 7. Departures from the 2026-10-28 plan are listed. N and F saving all seven steps, and A0 before S, are unlisted but harmless.
