Does a blind search recover the reuse labels of four hand-made changes whose label is known by construction?

2026-11-10 · provisional, no independent check · cluster debug L40, completed by its repair run E138 (jobs 57142 and 57208), $0 · experiments/reuse_variable_test

The question. Part 1 needs a working definition of reused against new. The second wording of reuse (glossary) looks at one variable the original model computes and asks how the fine-tune sets it. Before reading any real fine-tune, can its search find the right answer on changes whose label we know because we built them?

What we did. We added one small piece to the 67M model in four ways, each setting a four-direction variable in block 2. Always on sets it to a fixed value, trained so the model continues lowercased text, so it is re-weighted. Cue sets it from a linear read-out of block 1 that detects one rare token, and Table from a linear map of block 0 trained on 32 keys, so both are rewired. XOR sets it from the XOR of a random bit per token over the last four tokens, so it is built. A search that was not told the answer then measured two shares of the change, each from 0, nothing explained, to 1, all of it. The re-weighting share is how much an affine map of the variable itself explains. The rewiring share is how much an affine map of everything the model computed at that point explains.

What we found. The search reached every known answer it was set, above the 0.9 bar. The re-weighting share orders the pairs as their labels: Always on 0.922, Cue 0.666, XOR and Table just below zero. The rewiring share is near 1 on the three changes that are not built and just below zero on the XOR. The first wording calls the XOR reuse, so only the second wording matches its label.

What it means. The second wording can be measured, on known cases. With no cut-offs in this run these are orderings, not labels, and they follow the labels by construction. The next run asked whether ordinary fine-tunes that imitate the same four changes read the same way (E139).

Run
One test on the 67M on the cluster's debug queue, $0, finished by its repair run after a solver refusal and a card memory failure. The identity check ran first and alone and was exact on all four changes.
Found
  • As expected, the search reached every known answer and the two shares put the four changes in the order of their labels.
  • The XOR cannot be read linearly from the model: an affine read of it scores 0.506 against 0.502 for shuffled bits, so built is possible here.
  • Not expected, the rewiring search's last refinement made things worse at 19 of 20 places and was dropped, so a low rewiring share late in the model is a limit of the search, not evidence.
