Does the re-gating share read the kind of change built into a fine-tune?

2026-11-17 · cells P2.33 (runs 1 and 2 of 2; run 2 is E202, carded here) and P2.34 (E204, E207), provisional, no independent check · experiments/share_built_kind, experiments/share_size_matched

The question. Part 3 asks whether the re-gating share, the share of a fine-tune's gain that appears when the original subcomponents are kept and only the frozen gates switch them differently, tells re-weighting from rewiring. Here the kind of change is built in, so the answer is known in advance. Should a fixed push on the output read higher than a new map?

What we did. We took fifteen 67M fine-tunes, each trained to imitate a hand-made edit of one built kind: Always on (a fixed push, built re-weighting, six states), Table and Cue (new maps, built rewiring) and XOR (the fine-tunes learned nothing, a reference). We read the share on windows where the hand-made edit raises its top token by at least one log-odds. Before that we checked that the unchanged model reads exactly zero and that a saved state reproduces its saved share, 0.802.

What we found. Both controls held. Table reads about 0.26 on a gain of 19.1 log-odds; Always on reads 1.11 to 1.13, Cue 1.21 to 1.23 and XOR 1.10 to 1.12, all on gains of 1.07 to 1.77. Always on beat Table as filed, by 0.857, but fell 0.106 below Cue, the opposite of the filed direction. The first run's windows gave too little gain to read, except for Table.

What it means. On these fine-tunes the share does not tell built re-weighting from built rewiring: a rewiring fine-tune and one that learned nothing read like the re-weighting one. Its one split, Table against the rest, is also the only large-gain group, so gain size and built kind cannot be told apart here. Provisional until checked; the fine-tunes stay as labels for the share on the 67M.

Follow-up, no call (E204, E207; cell P2.34). To separate kind from size we tried to scale one hand-made edit to the other's size, before training anything. Scaled up, Always on never reaches Table's gain of 19.13 log-odds: it levels off at 16.0 by a factor of 256, and by 32 one token takes 0.91 of the windows against 0.05 unscaled, so it has stopped re-weighting. Scaled down, Table reaches Always on's gain of 1.69 at a quarter size but only 0.04 of its targets are then Table answers, against 0.77 at full size. Each edit keeps its built kind only near its own size, so the question stays open; no share was read, and the first reading stands.

Run
Two cluster debug jobs (run 1 job 60937, run 2 job 60967), one L40 each, $0. Both controls passed first. The size-matched follow-up: two RunPod L40S runs, $0.32 in all, each stopped at its filed check before any fine-tune.
Found
  • Table reads 0.26 on a large gain; Always on, Cue and XOR all read a little above one on small gains.
  • Always on above Table passed; Always on above Cue missed, reversed by 0.106.
  • Scaling either edit to the other's size lost its built kind first, so kind and size stay unseparated (no call).
Bears on
