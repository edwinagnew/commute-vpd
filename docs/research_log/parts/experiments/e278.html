Does the write share over the needed set tell copying from lookup, or order the five key tasks?

2026-11-23 · cell P1.57, definition-lead · experiments/eb_dropped, experiments/head_edit (E280), experiments/e62_copy_windows (E281)

The question. Two results dropped when the paper moved to its second draft were never read under the frozen definition: E62's copying-head pair (the user's worked example of reuse) and the five-task key grid at one update size. Does the write share over the needed set (the share of each needed variable's write change that lies along its original write, 1 for a pure rescaling) separate copying from lookup, and order the five tasks?

What we did. We read the saved states: three seeds each of E62's copy and lookup fine-tunes, and three seeds of each of the five key tasks, each task beside three random updates of the same size. Follow-ups (E280, E281) read the copy windows alone, and built edits that double only the copy head's value, output or query. A flip-weighted version was tried as a control.

What we found. No separation. All fifteen key-grid states read 0.027 to 0.040 against the filed gap of 0.2; the cipher sits highest on every seed, the reverse of the filed expectation, by a fortieth of the gap. Copy reads 0.004 below lookup on E62, and 0.53 to 0.61 of lookup on the copy windows alone, so the mix of windows is not diluting a difference. Doubling only the copy head reads about 0.2 at VPD, because VPD decomposes each attention matrix whole. The flip-weighted version failed its positive control.

What it means. The write share reads every trained update about the same small amount (two to three times a random update, a tenth of a pure strengthening edit), so it cannot say whether copying reuses the base model while a cipher is new. This is a run of instrument failures, not a negative result about reuse. Redteam: rival B as filed.
