Is a 67M fine-tune's gain fed through parts whose own weights barely changed, or written into changed ones?

2026-11-05 · cluster L40 debug, $0 · experiments/fed_or_written · provisional, independent check holds with a caveat

The question. You decided that a fine-tune gets a label (new or strengthened) only through a located mechanism ({{n:decisions}}). E97 could name the part only for copying. Does a number read from the weights alone, with no input pairs, tell a fine-tune built to reuse the original model's machinery from one built to write something new?

What we did. For every saved 67M fine-tune we set each of the 28 parts (24 attention heads, 4 feed-forward layers) back to the original model's weights, one at a time, and measured how much of the gain it took with it. A part whose own revert costs little while its output still matters is "fed" from upstream; one whose revert costs a lot is "written". We filed a per-part reading first. After it failed we noticed the sum of the 28 single reverts and tested that on states we had not read.

What we found. The filed per-part column did not track construction: it put both poles where we built them, but every key-table task landed "mixed" at the last feed-forward layer, and the copying and cipher tables fell on the same side. The sum of single reverts does sort them. Every copying fine-tune sums 0.22 to 0.40 and every task built with new answers 0.62 to 0.98, and on five unread seeds all 10 copy and cipher tables landed on their sides. The independent check holds this, with a caveat: only copy maps read low so far, and the bar moves with the site, because an update written by construction reads 0.64, 0.72 or 0.86 depending on the inputs.

What it means. This is evidence to set beside the new-against-reuse definition's verdicts, not a label. It separates copy maps from key-table maps; it does not yet separate reuse from new, since the one non-copy task built to reuse (rank-1, answering the original model's own top guess) reads written, and every low reading is a copy task. Rank-1 was filed "fed" and regrouped after the number was seen, so its reads are written, as read. Amendment 2 (reports/plans/2026-11-05_plan_e100-amend2.md, jobs 52989 and 53015, $0) did not change that: a bar that depends on the site was not adopted (gap 0.19, under the 0.22 filed), so the fixed bars stand. The emoticon trigger keeps its gain with E62's copying heads switched off (1.01 to 1.02, while the copy control loses 89%) and still reads fed (0.30 to 0.37), so "fed" is not only copy maps. The class map and the twin read mostly between, and the sharpen pair stopped on its filed rule (17 strong keys, under 24), so that column goes to definition-lead as the check worded it. E100's two amendments are spent.
